# Q4: 기술 단위와 변경 결

- 문항: 5개
- 권장 시간: 10분
- 범위: technical grain, 책임 있는 hop, deep module, chokepoint, change propagation, coverage boundary

## 1. Pass-through hop과 책임

`SearchFacade`는 인자를 그대로 `SearchService`에 넘기고 반환값을 같은 모양으로 돌려준다. 인증·정책·
오류 변환·관측·복잡성 은닉은 모두 `SearchService`가 수행한다.

**`SearchFacade`를 책임 있는 architecture boundary라고 볼 수 있는가? 제거 판단 전에 확인할 evidence와
반대편 비용을 적어라.**

<details markdown="1">
<summary>정답·판단 기준</summary>

현재 evidence로 `SearchFacade`는 제거해도 중요한 규칙이나 숨긴 복잡성이 달라지지 않는 pass-through
hop에 가깝다. 다만 실제 call graph와 대표 변경의 propagation을 추적하고, 안정된 interface·교체 seam·
관측 지점 같은 숨은 책임이 없는지 확인한 뒤 제거 비용과 결합도 증가라는 counter-cost를 함께 기록한다.

Q4는 계층 수를 줄이는 규칙이 아니라 선언한 기술 원칙과 실제 hop 책임이 맞는지를 보는 Architecture
Fitness lens다. 해당 원칙이나 관측 경로가 없다면 제거 권고를 확정 verdict로 바꾸지 않고 `unknown`으로
남긴다.

</details>

## 2. Chokepoint와 우회 경로

서비스 정책은 모든 외부 HTTP 요청이 timeout·retry·credential 규칙을 소유한 `ProviderGateway`를
통과해야 한다고 선언한다. 대부분의 호출은 이를 따르지만 새 report 모듈 하나가 provider에 직접
`fetch`한다.

**Q4 verdict를 판정하고, 회귀를 막을 기계적 evidence를 하나 적어라.**

<details markdown="1">
<summary>정답·판단 기준</summary>

승인된 gateway만 사용한다는 policy와 직접 `fetch`하는 정적 evidence가 같은 target revision에서
비교되므로 해당 case는 `degraded`다. Direct HTTP import·call을 금지하는 architecture lint나 guard를
CI에서 실행해 우회 edge가 생기면 실패시킨다.

Gateway가 유용한 이유는 hop 자체가 아니라 timeout·retry·credential effect policy를 한곳에서
소유하기 때문이다. Adapter는 call edge를 수집하고 core의 deterministic comparison이 verdict를
계산한다.

</details>

## 3. Change propagation과 policy 부재

한 필드의 의미를 바꾸자 API·service·repository 등 12개 모듈을 수정해야 했다. 팀은 수정 파일 수가
많다는 사실만으로 Q4를 `degraded`로 기록하려 한다.

**지금 곧바로 `degraded`라고 할 수 있는가? 확정 판정에 추가로 필요한 것을 적어라.**

<details markdown="1">
<summary>정답·판단 기준</summary>

수정 파일 12개만으로는 `degraded`를 확정할 수 없다. 허용 propagation 또는 책임 배치에 관한
consumer-owned policy, 정확한 before/after revision, 실제 변경 경로와 중복된 policy·effect evidence가
필요하다.

Policy가 없다면 Q4는 `unknown`이다. 선언된 단일 변경 지점이나 허용 경계를 12개 모듈이 재현 가능하게
위반했다면 그때 `degraded`이며, 파일 수가 많다는 일반적 미감만으로 판정하지 않는다.

</details>

## 4. Deep module과 계층 수

모듈 A는 공개 메서드 두 개 뒤에서 transaction, idempotency와 외부 effect 순서를 책임진다. 모듈 B는
내부 단계를 각각 wrapper로 공개해 caller가 여섯 메서드를 올바른 순서로 호출해야 한다.

**어느 쪽이 더 적절한 technical grain인가? Architecture Fitness 관점에서 무엇을 비교해야 하는가?**

<details markdown="1">
<summary>정답·판단 기준</summary>

주어진 조건에서는 작은 interface 뒤에 transaction·idempotency·effect ordering을 숨기는 A가 deep
module에 가깝다. B는 caller에게 순서와 실패 처리를 전파하므로 각 wrapper가 별도 policy를 소유하지
않는다면 high-propagation path가 될 가능성이 크다.

Architecture Fitness는 “적은 계층”을 보상하지 않는다. Consumer가 선언한 effect owner와 변경 locality,
caller가 알아야 할 복잡성, 분리했을 때 얻는 독립 배포·권한·교체 비용을 실제 call path와 함께 비교한다.

</details>

## 5. 부분 coverage와 adapter의 권한

Consumer adapter가 승인된 collector로 `external-http-gateway` guard를 실행했고, target revision과 전체
observation을 결속한 검증도 통과했다. 이 guard가 성공하자 adapter는 “Q4 전체 healthy”라는 verdict와
exit `0`을 반환했다. Hop 책임과 propagation은 수집하지 않았다.

**이 결과에서 잘못된 점과 올바른 coverage·verdict 표현을 적어라.**

<details markdown="1">
<summary>정답·판단 기준</summary>

Adapter가 verdict를 선언한 것이 잘못이며, exit `0`도 Q4 전체 health를 뜻하도록 해석하면 안 된다.
Adapter는 검증 가능한 observation만 만들고 core가 coverage에 포함된 `external-http-gateway` case의
`healthy`를 계산해야 한다.

Hop 책임과 propagation은 `unsupported` 또는 `excluded` 이유와 owner·재진입 trigger를 가진 coverage로
남기며 Q4 전체를 초록색으로 합치지 않는다. 승인된 collector와 HMAC 결속은 관측을 verdict에 참여시킬
필요조건이지, 관측하지 않은 case까지 healthy로 만드는 증거가 아니다.

</details>
