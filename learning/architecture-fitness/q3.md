# Q3: 확장성과 부하

- 문항: 5개
- 권장 시간: 10분
- 범위: workload envelope, 지속 부하, SLO break point, tail latency, queue와 backpressure,
  입력 cardinality와 amplification

## 1. One-shot cohort와 지속 처리 용량

로컬에서 사용자 20명이 동시에 한 번씩 검색했고 전부 3초 안에 성공했다. 팀은 이 결과만으로 “몇
시간 동안 요청이 이어져도 운영 처리 용량이 충분하다”고 결론 내리려 한다.

**이 결론이 성립하지 않는 핵심 이유를 설명하고, workload envelope에 추가로 고정해야 할 항목 세
가지를 적어라.**

<details markdown="1">
<summary>정답·판단 기준</summary>

20명이 한 번씩 성공했다는 결과는 짧은 동시성 spike만 증명하며, 시간이 지나면서 queue·memory·연결·
provider quota·retry가 누적되는 steady state를 증명하지 않는다. Workload envelope에는 arrival model과
요청률 또는 동시성, 지속 시간, 입력·결과 크기, provider 지연·오류 조건, 실행 topology 중 적어도 세
가지를 숫자와 함께 고정해야 한다.

외부 환경에서 시험하지 않았다는 점도 한계지만 핵심은 환경만이 아니다. 같은 로컬 환경에서도
one-shot cohort와 sustained traffic은 서로 다른 failure mode를 드러내므로, 외부 환경에서 one-shot을 한
번 더 실행하는 것만으로 지속 처리 용량이 증명되지는 않는다.

</details>

## 2. 첫 SLO break point와 운영 목표

검색 SLO는 p95 3초 미만이다. 같은 조건에서 다음 결과를 얻었다.

```text
동시 사용자 20명: p95 1.8초
동시 사용자 40명: p95 2.6초
동시 사용자 80명: p95 4.1초
```

**첫 SLO break point를 판정하고, 운영 동시성 목표를 곧바로 40명으로 정하면 안 되는 이유를
설명하라.**

<details markdown="1">
<summary>정답·판단 기준</summary>

관측된 첫 SLO break point는 80명이다. 정확한 경계는 40명과 80명 사이이므로 50·60·70명처럼 주변
구간을 반복 측정해 범위를 좁혀야 한다.

40명 통과는 측정 결과이지 운영 policy가 아니다. 반복 실행, 지속 시간, 운영 환경, provider 변동과
traffic spike를 흡수할 headroom을 고려해 목표를 정하며, 날짜나 기능 압박 때문에 break point에 바로
붙여 운영하지 않는다.

</details>

## 3. Tail latency와 causal evidence

동시 사용자가 40명에서 60명으로 늘었을 때 평균 latency는 계속 1초지만 p95는 2초에서 4초로
증가했다. 측정 결과 provider 호출은 계속 1초이고 queue wait p95는 0.2초에서 2.2초로 증가했다.

**“전체 latency가 선형 증가했다”는 설명이 적절한가? 우선 조사할 병목과 그 판단을 뒷받침하는
evidence를 적어라.**

<details markdown="1">
<summary>정답·판단 기준</summary>

전체 latency가 선형 증가했다고 말할 수 없다. 동시성은 50% 증가했지만 p95는 100% 증가했고 평균은
그대로이므로, 다수의 빠른 요청보다 느린 꼬리 요청이 급격히 악화된 상태다.

Provider 시간은 일정하고 queue wait가 2초 늘었으므로 우선 조사할 병목은 내부 admission·동시 처리
슬롯·queue다. 요청별 trace나 phase timing, queue depth·wait, active in-flight, 처리 throughput을 함께
측정해 provider 지연과 내부 대기를 인과적으로 분리한다. 두 지점만으로 장기 곡선이나 근본 원인을
확정하지는 않는다.

</details>

## 4. Provider 지연, queue와 load shedding

동시 처리 슬롯은 10개다. 정상 상태의 요청 처리 시간은 0.5초지만 provider가 느려지면 2.5초가
걸린다. 서비스에는 초당 8개 요청이 계속 들어오며 검색 SLO는 3초다.

**Provider 저하 중 queue가 계속 길어지는 이유를 설명하고, worker를 100개로 늘리는 것만으로 충분하지
않은 이유와 필요한 보호 장치 두 가지를 적어라.**

<details markdown="1">
<summary>정답·판단 기준</summary>

처리 용량은 대략 `동시 처리 슬롯 ÷ 요청 처리 시간`이다. 정상 상태에는 초당 약 20개를 처리하지만
provider 저하 중에는 초당 약 4개만 처리하므로, 초당 8개가 들어오면 backlog가 매초 약 4개씩 늘어난다.

Worker를 늘리면 잠시 queue를 흡수하지만 provider 동시 호출·비용·quota 사용을 늘리고, provider가 이미
과부하라면 장애를 더 증폭시킨다. Bounded queue와 bounded concurrency, timeout·cancellation,
backpressure, 제한적인 retry, SLO 안에 처리할 수 없는 요청의 load shedding 중 두 가지 이상을 실제
failure mode에 맞게 적용한다.

검색 SLO가 3초인데 예상 queue wait가 이미 5초라면 조용히 쌓아 두지 않고 명시적인 429·503과 재시도
정책으로 빠르게 거절하는 편이 적합할 수 있다. 빈 검색 결과로 위장하면 정상적인 결과 없음과 과부하를
구분할 수 없으므로 outcome 의미도 함께 보존해야 한다.

</details>

## 5. 입력 크기, `O(n²)`과 비례성

두 서비스의 처리 SLO는 3초다. 서비스 A는 결과를 최대 20개로 제한하는 제품 policy와 runtime guard가
있고 모든 결과 쌍을 비교한다. 목표 동시성 × 20개 경계에서 반복 부하 테스트가 SLO를 만족한다. 서비스
B는 1,000개 결과를 지원해야 하지만 같은 pairwise 후처리에서 10개는 0.1초, 100개는 4초, 1,000개는
59초가 걸린다.

**`O(n²)` 후처리를 모든 서비스에서 금지해야 하는가? A와 B를 각각 판정하고, A의 결정을 안전하게
유지할 구조적 방어를 적어라.**

<details markdown="1">
<summary>정답·판단 기준</summary>

`O(n²)` 자체를 모든 서비스에서 금지하지 않는다. A는 제품이 선언한 작은 상한을 경계에서 강제하고
목표 동시성의 반복 runtime evidence가 있으므로 현재 envelope에서는 `healthy`일 수 있다.

B는 1,000개 지원 policy와 3초 SLO에 실제 59초 후처리가 비교 가능한 mismatch이므로 `degraded`다.
Provider 시간이 일정하다면 중첩 순회, 항목별 DB/API 호출, 반복 정렬·복사 같은 내부 work
amplification을 우선 조사하고 알고리즘 변경, pagination·streaming 또는 Human이 승인한 제품 상한을
비교한다.

A의 구조적 방어에는 입력 상한의 runtime validation, 최대 입력 × 목표 동시성 성능 test, 상한·동시성·
알고리즘 변경 시 review를 다시 여는 trigger가 포함된다. 입력 cap을 코드에만 숨기거나 한 명 × 최대
입력과 최대 사용자 × 작은 입력을 따로 통과한 결과만으로 결합 workload를 healthy로 만들지 않는다.

</details>

## 기술 근거

- Google SRE, [Addressing Cascading Failures](https://sre.google/sre-book/addressing-cascading-failures/):
  overload, queue, retry amplification과 load shedding을 함께 판단하는 근거다.
- Grafana k6,
  [Open and closed models](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/):
  시스템이 느려질 때 요청률까지 낮아지는 closed model과 독립적인 arrival rate를 유지하는 open model을
  구분하는 근거다.
- Gunther·Holtman,
  [Getting in the Zone for Successful Scalability](https://arxiv.org/abs/0809.2541): 충분한 load point에서
  concurrency 증가와 throughput·contention 곡선을 해석하는 참고다.
