# Q5: 캐시 전략

- 문항: 5개
- 권장 시간: 10분
- 범위: cache owner, key scope, freshness, invalidation, stampede control, process-vs-fleet semantics

## 1. 높은 hit ratio와 policy 부재

한 cache의 hit ratio는 95%이고 latency도 줄었다. 그러나 source owner, 허용 stale 시간, invalidation
trigger와 장애 시 행동을 선언한 문서는 없다.

**Q5 verdict를 판정하고, hit ratio만으로 `healthy`가 되지 않는 이유를 설명하라.**

<details markdown="1">
<summary>정답·판단 기준</summary>

Cache policy와 owner가 없으므로 Q5는 `unknown`이다. Hit ratio와 latency는 비용 효과를 보여줄 뿐,
잘못된 principal의 값이나 오래된 결과를 빠르게 반환하지 않는다는 correctness를 증명하지 않는다.

Source of truth, key scope, freshness·invalidation, stampede control, process-vs-fleet 의미를 선언하고 miss·
stale·concurrent fill을 재현 가능한 observation으로 비교해야 Architecture Fitness verdict를 계산할 수 있다.

</details>

## 2. Cache key와 결과 identity

Gap report의 내용은 `reportId`, 로그인 principal, locale, prompt policy version에 따라 달라진다. Cache
policy도 이 네 값을 key scope로 선언하지만 구현은 `reportId`만 key로 사용한다.

**Q5 verdict와 가장 위험한 failure mode를 적고, 필요한 검증을 하나 제안하라.**

<details markdown="1">
<summary>정답·판단 기준</summary>

선언된 네 차원과 `reportId` 하나뿐인 실제 key가 비교 가능한 mismatch이므로 `degraded`다. 다른 사용자·
locale·prompt version의 결과가 충돌해 권한 경계나 의미적 identity를 넘는 잘못된 report를 반환하는 것이
가장 위험하다.

한 차원씩 값을 달리하고 나머지는 고정한 collision test를 실행해 서로 다른 cache entry 또는 miss가
발생하는지 확인한다. Adapter는 key observation을 만들고 core가 policy ref와 observed ref를 비교한다.

</details>

## 3. Process-local cache와 fleet 의미

서버 인스턴스가 세 개이며 각자 메모리 cache를 가진다. 첫 요청이 인스턴스 A를 채운 뒤 다음 요청은
인스턴스 B로 이동해 다시 provider를 호출했다.

**이 구현은 무조건 `degraded`인가? 서로 다른 두 policy에서 verdict가 어떻게 달라지는지 설명하라.**

<details markdown="1">
<summary>정답·판단 기준</summary>

Process-local cache 자체는 잘못이 아니다. Policy가 “인스턴스 하나의 반복 호출만 줄이는 disposable
optimization”이라면 instance 이동의 miss는 허용되며 나머지 required check도 맞을 때 `healthy`일 수 있다.

반대로 fleet 전체에서 한 번만 fill하거나 durable reuse를 약속했다면 B의 재호출은 `degraded`다. Instance
이동, 동시 fill 수, 배포·재시작 뒤 행동을 관측해 선언된 state scope와 비교해야 한다.

</details>

## 4. Freshness와 invalidation

제품 Promise는 라이브러리 수정 직후 다음 조회에서 새 결과를 보여주는 것이다. Cache TTL은 30분이고
라이브러리 수정 이벤트에 연결된 invalidation이나 validation은 없다. 재현 테스트에서도 10분 동안 이전
결과가 반환됐다.

**Q5 verdict를 판정하고, TTL을 5분으로 줄이는 것만으로 충분한지 설명하라.**

<details markdown="1">
<summary>정답·판단 기준</summary>

즉시 반영 Promise와 10분 stale read가 같은 조건에서 확인됐으므로 `degraded`다. TTL을 5분으로 줄여도
최대 5분 stale을 허용하므로 즉시 반영 정책과 계속 불일치한다.

Write-triggered invalidation, versioned key 또는 source validation처럼 Promise를 강제하는 구조가 필요하다.
수정 직후 read, invalidation 실패, 여러 인스턴스로의 이동을 포함한 테스트로 다시 판정한다.

</details>

## 5. Concurrent fill과 stampede

비싼 provider 결과가 만료된 직후 같은 key로 100개 요청이 동시에 들어와 provider도 100번 호출됐다.
Policy는 key당 동시 fill 하나와 최대 2초 대기를 선언한다.

**Q5 verdict를 판정하고, 필요한 보호 구조와 failure-path 검증을 적어라.**

<details markdown="1">
<summary>정답·판단 기준</summary>

Key당 fill 하나라는 policy에 대해 100개 provider 호출이 재현됐으므로 `degraded`다. Per-key single-flight
또는 request coalescing, bounded wait와 concurrency, 만료 jitter 같은 구조로 refill amplification을
제한한다.

성공 경로만 보지 말고 leader timeout·오류·취소 때 waiters가 2초 안에 종료되고 다음 fill이 복구되는지
검증한다. 오류를 negative cache한다면 정상적인 결과 없음과 장애를 구분하고 별도의 freshness policy를
가져야 한다.

</details>
